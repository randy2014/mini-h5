## 一、现状：为什么需要一份全局清单

当前 H5 **没有任何全局权限层**，判断散落在各页面，且各页面口径互不一致：

| 位置 | 现用判据 | 问题 |
|---|---|---|
| `src/router/index.js:50` | `to.meta.auth` | **所有路由都没声明 `meta.auth`** → 守卫形同虚设，无第一道防线 |
| `pages/BookshelfPage.vue:44` | `userStore.isAuthenticated` | 正确 |
| `pages/VipPage.vue:170` | `localStorage.getItem('mini_novel_auth_token')` | 绕过 Pinia store，与书架页口径不同 |
| `pages/SubscribePage.vue:67` | `userStore.isVip` | 匿名与非VIP 共用同一套"无权限"文案 |
| `pages/SubscribeChannelPage.vue:88` | 后端 `restricted` 字段 | 唯一用后端自描述标记的页面 |
| `pages/ReaderPage.vue:137-143` | **任何异常**都弹"需要 VIP" | 网络失败 / 404 也被判成"需要 VIP" |
| `pages/CoinPage.vue` / `TicketPage.vue` | 无任何守卫 | 匿名可直达，表现为"空壳 + toast" |

后端同样没有全局鉴权：**无拦截器 / 无过滤器 / 无 `@SaCheckLogin` 类注解**，39 个 H5 端点全部靠 Controller 方法体内逐条 `if` 判断。

> **结论**：权限体系需要分两层建设 —— 前端负责「判定 + 拦截 + 提示」的统一体验，后端负责逐条兜底（真正的安全边界）。前端拦截**不是**安全措施，只是体验措施。

## 二、状态模型

### 2.1 六个正交维度

| 维度 | 取值 | 权威判定依据 | 前端可判定性 |
|---|---|---|---|
| **A 登录态** | `A0` 匿名 / `A1` 已登录 | Sa-Token token 有效（header `Authorization` 或同名 cookie）；后端返回 `code=401` | ✅ 可靠 |
| **B VIP 态** | `B0` 非VIP / `B1` VIP有效 | `app_user.vip_expire_time > now()` ——**唯一依据** | ✅ `/api/vip/status` 的 `active`，或 `/api/user/profile` 的 `vipActive` |
| **C 试用态** | `C0` 非试用 / `C1` 试用中 | `app_user.vip_activated_at + 7天 > now()` | ⚠️ 需前端自算，profile 返回 `vipActivatedAt` |
| **D 频道订阅态** | `D0` 未订阅 / `D1` 已订阅有效 | `user_subscribe`：`status='ACTIVE' AND end_time > now()` | ⚠️ 有污染，见 §2.4 |
| **E 快乐币余额** | `E0` 足够 / `E1` 不足 | `/api/coin/balance` vs 价格表（WEEK 100 / MONTH 300 / QUARTER 800 / YEAR 3000） | ✅ 但**价格不由接口下发**，需前端常量或新增接口 |
| **F 成人内容确认** | `F0` 未确认 / `F1` 已确认 | 本机 `localStorage.mini_novel_vip_adult_confirmed` | ✅ |

### 2.2 ⛔ 明确不可用于判权的字段

| 字段 | 为什么不能用 |
|---|---|
| `app_user.vip_status`（0/1/2） | 不参与任何后端判定，且 VIP 自然过期无清理任务 → 长期失真 |
| `Chapter.readable` / `Chapter.reviewStatus` | `@TableField(exist=false)` 且从未赋值，JSON 里恒为 `null`，是死字段 |
| `Chapter.priceCoin` | 被写入（VIP 章 = 10）但**全仓无任何扣币/解锁逻辑** |
| `Novel.freeChapterCount` | H5 读路径完全不使用；免费章节靠逐章 `is_vip` 标记实现 |
| 请求头 `X-User-Id` | 后端刻意忽略（`CurrentUserResolver.java:22`），前端仍在发，属死代码 |
| 后端 `message` 字符串 | "需订阅"与"账号被禁用"共用 `code=403`，只能靠上下文而非文案区分 |

### 2.3 组合态（矩阵列）

| 编号 | 组合 | 说明 |
|---|---|---|
| **S1** | `A0` | 匿名 |
| **S2** | `A1·B0` | 已登录 · 非VIP |
| **S3** | `A1·B1·C1` | VIP · **试用期内**（7 天全频道开放，等价于"全频道已订阅"） |
| **S4** | `A1·B1·C0·D0` | VIP · 试用结束 · **未订阅**该频道 |
| **S5** | `A1·B1·C0·D1` | VIP · 试用结束 · **已订阅**该频道 |
| 动作态 | `E1` | 快乐币不足：**仅**影响"订阅 / 一键订阅"动作 |
| 页面态 | `F0` | 未做 18 岁确认：**仅**影响 VIP 专区 |

**S2 必须再分两种成因**（提示文案不同）：

| 子态 | 判定 | 文案方向 |
|---|---|---|
| `S2a` 从未 VIP | `vipExpireTime == null` | "用邀请码开通 VIP" |
| `S2b` VIP 已过期 | `vipExpireTime != null && < now()` | "VIP 已到期，续期后继续" |

**⚠️ D 维度独立于 B 维度**：订阅关系不会因 VIP 过期而消失。因此存在 `A1·B0·D1`（VIP 过期但频道订阅仍在）这一组合 —— 此时**频道媒体仍可看，但频道内 `vipRequired` 的小说一律 403/2001**。矩阵中按"S2·D1"处理。

### 2.4 两个必须记住的后端真相（决定矩阵形状）

#### 真相 1：VIP 与订阅是两个**正交**权限域，且**订阅不覆盖小说**

```java
// NovelController.java:100 —— 章节正文门禁，订阅完全不参与
if (Boolean.TRUE.equals(chapter.getVip()) && !vipAccessService.hasActiveVip(resolvedUserId)) {
    throw new BusinessException(ErrorCode.VIP_REQUIRED, "该章节需要开通 VIP 后阅读");
}
```

由此产生两个反直觉结论：

- **已订阅频道 A、但 VIP 已过期** → 频道 A 的媒体能看，频道 A 里的 `vipRequired` 小说**看不了**（详情/目录/正文全部 403）。
- **有 VIP、但一个频道都没订阅** → 能读**全网**任意 VIP 小说的非免费章节（只要拿到 novelId / chapterId）。

→ 前端**绝不能**把"已订阅该频道"渲染成"该频道内容均可读"。

#### 真相 2：频道媒体完全由订阅（或试用）控制，且**无预览态**

| 端点 | 未订阅（试用已结束）时 |
|---|---|
| 频道 feed | 媒体项**被整体剔除**（列表里根本不存在），小说项照常返回 |
| `/media/posts/{id}` 媒体帖详情 | **403 + `"订阅后查看"`** |
| `/media/assets/{id}/file` 媒体字节 | **403**，`full` / `thumb` / `poster` **一律拒绝**（缩略图也没有） |
| 频道小说列表 | `restricted=true` + **第 1 页完整小说元数据**（有预览） |

### 2.5 由此收敛出的 5 个「能力域」

权限模型建议**只暴露能力域，不暴露状态**——页面问"我能不能做 X"，而不是自己拼 6 个状态条件。

| 能力域 | 判定式 | 覆盖功能 |
|---|---|---|
| **P0 公共阅读** | 恒真 | 首页、分类、榜单、搜索、免费书详情与章节 |
| **P1 VIP 阅读** | `B1` | VIP 小说详情/目录、`is_vip` 章节正文、VIP 专区书单 |
| **P2 频道媒体** | `C1 ∨ D1(该频道)` | 频道 feed 内图文/视频、媒体帖详情、媒体字节 |
| **P3 交易** | `A1 ∧ E0` | 订阅频道、一键订阅、续订 |
| **P4 账户** | `A1` | 书架、账户级阅读历史、工单、快乐币、昵称 |

> ⚠️ **搜索是本项目最隐蔽的权限差异**：同一 URL 同一参数，几种登录态返回不同集合，且响应**没有任何标记**
> 说明结果被裁剪过：
>
> | 登录态 | 返回 |
> |---|---|
> | 匿名 / 非VIP | 仅免费小说 |
> | VIP 试用期内 | 免费 + **全部** VIP 小说 |
> | VIP + 已订阅部分频道 | 免费 + **仅订阅频道内**的 VIP 小说 |
>
> → 前端无法区分"真的没有结果"和"有结果但你看不到"。**需要后端补 `restricted` 类标记**（见 §7）。
>
> 📌 **搜索与 VIP 专区货架的关系（2026-09-13 定：搜索保持现状，不随货架变化）**：
> 已发布频道的小说不出现在 VIP 专区，但仍可能出现在搜索结果里（取决于上表口径）；
> **已知并接受**：频道下架后小说回到 VIP 专区，但普通 VIP（无订阅、非试用）**依然搜不到**它 ——
> 因为搜索对无订阅的 VIP 只返回免费书。若要改变需单独决策（会同时影响订阅用户的搜索体验）。

## 四、提示与引导规范

### 4.1 五级提示层级

| 层级 | 形态 | 适用 | 现有实现参考 |
|---|---|---|---|
| **L0** | 整页替换（页面主体换成门禁卡） | 整页都不可用 | `VipPage` 的 `vip-access-denied`、`BookshelfPage` 的 `no-login` |
| **L1** | 区块占位（页面内某区块换成锁定卡） | 页面部分可用 | `SubscribeChannelPage` 的 `footbar` 订阅条 |
| **L2** | 操作级提示（toast / 确认弹窗） | 可见但不可点 | `ReaderPage` 的"需要 VIP"弹窗 |
| **L3** | 按钮态（置灰 / 加锁图标 / 禁用态文案） | 入口保留但不可用 | `VipPage` 的 `subscribe-prompt` |
| **L4** | 静默降级（该内容不渲染） | 不需要解释的裁剪 | 未订阅时媒体项不出现 |

### 4.2 门禁原因 → 提示文案 → 引导落点（唯一文案出口）

| 门禁原因 | 触发条件 | 层级 | 文案 | 主按钮 / 落点 |
|---|---|---|---|---|
| `NEED_LOGIN` | `A0` 且能力需登录 | L0 | 「登录后同步你的书架和阅读记录」/「登录后可继续」 | 立即登录 → `/h5/login?redirect=<当前全路径>` |
| `NEED_VIP`（从未开通） | `B0` 且 `vipExpireTime == null` | L0/L1 | 「该内容需要 VIP 资格，可用邀请码开通」 | 使用邀请码 → `/h5/vip`（登录页邀请码入口） |
| `VIP_EXPIRED` | `B0` 且 `vipExpireTime < now()` | L0 | 「VIP 已到期，续期后可继续阅读」 | 去续期 / 联系客服 |
| `NEED_CHANNEL_SUBSCRIBE`（媒体） | `P2` 不成立 | L1 | 「订阅后可查看本频道的图文与视频」 | 订阅本频道（300 币/月） |
| `NEED_CHANNEL_SUBSCRIBE`（小说预览） | `P2` 不成立，S4 | L2/L3 | 「订阅后查看该频道全部小说」 | 同上一行 |
| `NEED_COIN` | `E1` 且动作需扣币 | L2 | 「快乐币余额不足」+ 当前余额 / 所需数量 | 去快乐币页（或联系客服充值） |
| `ADULT_CONFIRM` | `F0` 且进 VIP 专区 | L0（页内门禁） | 「本频道含成人主题内容，仅面向已满 18 周岁用户」 | 勾选确认 → 进入 |
| `ACCOUNT_DISABLED` | 后端 403「账号已被禁用」 | L0 | 「账号已被禁用，请联系客服」 | 联系客服 |
| `NETWORK_ERROR` | 非权限类异常 | L2 | 「网络异常，请重试」 | 重试按钮 |

### 4.3 五条硬规则

1. **禁止用异常反推权限**。`ReaderPage.vue:137-143` 的"任何 catch 都弹需要 VIP"是反面教材 —— 网络失败、404、超时全被误判。必须先按业务 code 分类，再决定提示。
2. **权限提示必须带明确落点**。只弹 toast 不给按钮 = 用户无路可走。
3. **文案集中在 `prompts.js`，不直接透出后端 `message`**。原因：`code=403` 同时表示"需订阅"和"账号被禁用"，匹配中文字符串对文案改动极其脆弱。
4. **同一门禁在同一会话内只弹一次**，后续降级为 L3/L4，避免反复打断。
5. **可预判的不要等后端拒绝**。资源自带 `Novel.vipRequired` / `Chapter.vip` 字段 → 进页面前就能判定，不该先发一次注定 403 的请求。

## 五、门禁错误码映射（前端归一化）

| 后端 `code` | HTTP 状态 | 语义 | 前端动作 |
|---|---|---|---|
| `401` | **401** | 需登录 | 清会话（**含 Pinia store**）→ 跳登录（带 redirect） |
| `2001` | **403** | 需 VIP | L0/L1 VIP 引导，**不弹通用错误** |
| `403` | **403** | 需订阅 **或** 账号被禁用 | ⚠️ **无法区分** → 需按调用上下文判断；建议后端拆码（§7.1） |
| `1000` | **200** ⚠️ | 业务失败（余额不足 / 验证码 / 参数 / 限流） | **必须按 `code` 判，不能按 HTTP 状态** —— 按状态判会把失败当成功 |
| `404` | 404 | 资源不存在 | 常规空态 |
| 无 `code` 字段 | 任意 | 非业务异常 / 网关错误 | 归为 `NETWORK_ERROR`（`GlobalExceptionHandler` 不捕获非 `BusinessException`） |

### 前端必须修的两处（当前阻碍权限体系）

```js
// src/services/http.js:38-45 —— 错误分支丢弃了业务 code
const message = error.response?.data?.message || error.message || '网络异常';
return Promise.reject(new Error(message));   // ← 调用方拿不到 code
```

- **问题 1**：`403-需订阅` 与 `403-需 VIP(2001)` 在 HTTP 错误路径上**无法区分** —— 而 2001 走的正是这个分支。
- **问题 2**：`http.js:29-31` 401 时只清 `localStorage`，**不清 Pinia store** → 出现"store 认为已登录、页面拿不到数据"的错乱态，且不跳登录页。

→ 需要归一化为 `{ code, httpStatus, message }` 结构，并由 `errors.js` 映射到 §4.2 的门禁原因。

## 八、前端权限层结构（✅ 已落地 2026-09-13）

```text
src/permission/
  constants.js      // 状态枚举、能力域 P0~P4、门禁原因、提示层级、试用天数、价格兜底
  rules.js          // buildSnapshot / can / activeSubscription —— 纯函数，可 node:test
  errors.js         // ApiError + 后端 code/HTTP → 门禁原因 归一化（纯函数）
  prompts.js        // 门禁原因 → { level, title, text, action, toast } —— 唯一文案出口
  store.js          // usePermissionStore：订阅集合 / 余额 / 成人确认 + snapshot getter
  useCapability.js  // useCapability() → { can, check, prompt, subscribeGate }
  guard.js          // resolveNavigation + 守卫安装（meta.require）
  session.js        // 401 → 清 store + 跳登录（连带原始去向）
  index.js          // 出口 + installPermission(router)
```

配套：`npm test`（52 个用例）与 `npm run verify`（SFC 编译 + import 解析 + pinia 集成冒烟）。

设计要点：

1. **状态唯一来源是 `permissionStore`**，由 profile + 订阅接口（或 §7.3 的聚合接口）刷新；页面**不直接读 localStorage**。
2. **页面只问"能力"，不问"状态"**：`can('VIP_READ')`，而不是自己拼 `isAuthenticated && profile?.vipActive`。
3. **路由 meta 只做整页级拦截**（L0）；区块级门禁用 `useCapability` 在组件内做。
4. **模块化能力域可扩展**：将来加"单章币解锁""免费试读 N 章"时，只需在 `useCapability` 加一条规则，不用改页面。
5. **后端仍是唯一安全边界**：前端门禁被绕过时，仍应收到 401/2001/403，并由 `errors.js` 兜底转成同一套提示。
